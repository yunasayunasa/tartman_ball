## 1. この文書の目的と読み方

本書は、発注者との過去の会話を知らないエンジニアが、設計・実装・実機検証・公開・引き継ぎまで進めるための仕様書である。

本書中の区分は次の意味を持つ。

- **確定仕様**：発注者と合意済みの要求。削除・変更する場合は事前合意が必要。
- **実装指針**：確定仕様を満たすための推奨方法。外部から見える仕様を変えなければ、エンジニアの判断で同等以上の方法を選択できる。
- **調整項目**：実機プレイを通して決める数値や配置。初期値を設定し、試遊結果をもとに調整する。
- **要支給・要確認**：素材・アカウント・検証端末など、発注者側の情報や協力が必要な事項。

特定の実装手段を守ることより、操作の気持ちよさ、落下の緊張感、クリアの達成感、スマホで安定して遊べることを優先する。新機能を増やして品質や完成を遅らせない。

## 2. 企画概要

### 2.1 作るもの

スマートフォンを縦に持ち、端末を傾けて透明なボールを操り、空中に浮かぶコースのゴールを目指す3Dブラウザゲーム。ボールの内部には、発注者が支給するキャラクターを配置する。

参考となる遊びは『スーパーモンキーボール』。見た目の方向性は『グランブルーファンタジー』から連想される青空、白い雲、明るい空の世界。ただし、既存ゲームのコード・コース・画像・音源を複製する発注ではない。支給素材を除き、本作向けの独自表現で構成する。

### 2.2 体験の柱

1. **身体とゲームの連動**：実際にスマホを傾けた方向と強さが、球の加速や曲がり方として伝わる。
2. **落ちそうな緊張感**：慣性、細い足場、曲がり角、空中移動によって慎重な操作が必要になる。
3. **突破する達成感**：ダッシュパネルとジャンプ台をうまく使い、着地やゴールを決める。
4. **気軽な再挑戦**：残機や制限時間を設けず、落ちても近くから再開できる。

### 2.3 今回の完成範囲

発注者の希望は「完成度8割ほど」。これは機能の2割を未実装にしてよいという意味ではない。**全5コース、支給キャラクター、画面遷移、記録、基本演出を揃え、残作業が主に操作感・難易度・見た目の追加調整となる状態**を指す。

必須仕様の未実装、進行不能、不安定な入力、頻繁な描画停止を「残り2割」として扱わない。

## 4. プレイの流れと画面

### 4.1 基本フロー

起動・素材読み込み → エリア選択 → 操作準備 → コース開始 → 走行／落下復帰 → ゴール → リザルト → 再挑戦またはエリア選択。

画面数を増やす必要はない。タイトルとエリア選択、操作説明と操作準備などは同じ画面内にまとめてよい。

### 4.2 必要な表示・操作

| 場面 | 必要な内容 |
| --- | --- |
| 起動・読み込み | 読み込み中と分かる表示。GLB等の読み込み失敗時は原因の分かる短い案内と再試行手段 |
| エリア選択 | 5コースの名前・特徴・ベストタイム・最多タルト数・全収集マーク。未プレイは未記録と表示 |
| 操作準備 | 傾き／スティック選択、短い操作説明、傾きの許可と基準登録、開始操作 |
| プレイ中 | 経過タイム、タルト取得数／総数、中断操作、必要最小限の案内 |
| 設定・中断 | 再開、操作方式変更、傾き感度、基準リセット、ミュート、最初から再挑戦、エリア選択へ戻る |
| リザルト | 今回のタイム、タルト数、自己ベスト更新表示、全収集表示、再挑戦、エリア選択 |

実装指針：操作方式・感度・ミュート設定も端末に保存するとよい。設定画面に入力カーブや物理係数などの開発者向け調整項目を大量に露出しない。

### 4.3 ラウンドの定義

「1ラウンド」は、コースを最初から開始してからゴールまたは離脱するまでの1回のプレイを指す。

- 落下復帰、チェックポイント復帰、一時中断は同一ラウンドを継続する。
- 「最初から再挑戦」は新しいラウンドとし、タイム・タルト・通過チェックポイント・復帰履歴を初期化する。
- エリア選択へ戻る操作は現在のラウンドを終了する。
- ページ再読み込みやブラウザ終了後の途中ラウンド復元は今回の対象外。保存済みのベスト記録は保持する。

## 5. 操作仕様

### 5.1 傾き入力

確定仕様：スマホを傾けた方向へ球を操縦する。端末の基準姿勢は、プレイヤーが自然に持った角度とする。机に水平に置くことを強制しない。

実装指針：DeviceOrientationを主入力候補とし、必要に応じてDeviceMotionを利用する。生の加速度だけを積分して球の位置を求める構成は採用しない。

入力処理は、概ね以下の順とする。

1. センサーの利用可否・権限・実際の値の受信を確認する。
2. 画面の向きを考慮して端末姿勢を解釈する。
3. 開始時に登録した基準姿勢からの傾きを算出する。
4. 微小な揺れを除き、必要最小限の平滑化を行う。
5. 小さな傾きでは精密操作、大きな傾きでは強い入力になる応答カーブを適用する。
6. 入力を正規化して、球のコントローラーへ渡す。

デッドゾーン、最大入力となる角度、応答カーブ、平滑化の強さは調整項目。微小な入力を消しすぎて操作が鈍くならないよう、実機で決める。

### 5.2 基準登録・権限

- 開始操作をきっかけに、必要な端末ではセンサー権限を要求する。
- 有効なセンサー値を受信してから基準角度を登録する。
- 基準リセットは専用の明示的な操作で行う。画面のどこをタップしても基準が変わる仕様にはしない。
- 権限拒否、非対応、値の受信失敗時は無反応のまま待たせず、スティックへ切り替える案内を出す。
- HTTPS公開環境で検証する。

実装指針：端末をほぼ直立させた場合や角度の境界で入力が反転・急変しないよう、姿勢の相対回転等を検討する。センサーAPIの存在だけで対応済みと判定しない。

### 5.3 スティック

- タッチ位置の移動量に応じて強弱を付けられるアナログ操作とする。
- 指を離す、タッチがキャンセルされる、画面を離れる場合は入力を解除する。
- 球の物理挙動は傾きモードと共有する。スティック専用の別ゲームにしない。
- スティックモードだけでも5コースすべてをクリア可能にする。

### 5.4 座標と慣性

- 画面の右へ傾けると画面の右方向へ、前へ倒すと画面の奥方向へ加速する。
- 傾きを戻しても球が即停止するのではなく、慣性が残る。
- 逆方向の入力で減速し、その後に逆方向へ移動できる。
- 空中では弱い軌道補正を許可する。踏み切りの失敗を自由な空中移動で完全に帳消しにしない。
- キーボード入力を開発確認用に設けてもよいが、製品としてのゲームパッド対応等は追加しない。

## 6. 球・カメラ・キャラクター

### 6.1 球の物理

確定した技術方針：Three.jsで描画し、Rapierで球と足場の物理を扱う。床と下向き重力を固定し、傾きに応じて球に横方向の力を加える。見た目だけ床を傾ける演出は初回に含めない。

実装指針：球を動的剛体、足場を固定コライダーとする。単純な形状でコースを構成し、必要のない複雑なメッシュ衝突判定を増やさない。固定時間刻みで物理更新し、描画フレームレートによって速度やジャンプ距離が大幅に変わらないようにする。

最高速度、摩擦、減衰、反発、入力加速度、空中補正量は調整項目。ダッシュ速度で足場をすり抜けないよう、高速移動時の衝突検出を検証する。

### 6.2 カメラ

- 球の位置へ滑らかに自動追従する。
- 方位を固定し、球の回転を追従対象にしない。
- 移動方向に合わせてカメラが旋回し、操作方向が変わる仕組みは設けない。
- 縦画面で次の足場、曲がり角、ジャンプ先が見える構図にする。
- 落下を延々追いかけたり、復帰時に長距離を横切るようなカメラ移動を避ける。

距離、高さ、視野角、追従速度は調整項目。回り込む手動カメラを必要とするコース設計は避ける。

### 6.3 キャラクター

- 発注者支給のGLBを使用する。走行アニメーションが含まれることは確認済みだが、ファイル自体は未支給。
- キャラクターの周囲を透明な球で覆い、足場・キャラクター・球の輪郭が見分けられるようにする。
- キャラクターは球の回転と切り離し、頭を上に保つ。
- 実際の移動方向へ滑らかに向きを変える。停止付近で細かく向きが振動しないようにする。
- 接地中は移動速度に合わせて走行モーションを再生する。空中では走行再生を止める。
- 待機や空中専用モーションは必須ではない。支給素材に存在する場合は利用してよい。

実装指針：GLBの向き、縮尺、足元、アニメーション名を検査する。走行クリップにルート移動がある場合は、キャラクターが球から飛び出さないよう、実行時の複製クリップ等でその場走行に調整する。元の支給GLBは保持する。

## 7. コースとギミック

### 7.1 コース構成

以下は合意した5コースの役割。名称、地形の寸法、タルト数、チェックポイント数は制作時に調整する。

| コース | 主題 | 必要な遊び |
| --- | --- | --- |
| 1 | 基本操作 | 広い道と緩いカーブ。傾き、加速、減速、収集、ゴールを自然に覚える |
| 2 | 精密操作 | 細い道と曲がり角。慣性を抑えながら通る緊張感 |
| 3 | ダッシュ | ダッシュパネルで加速し、その先の進路や減速を考える |
| 4 | ジャンプ | ジャンプ台から離れた足場へ着地する |
| 5 | 組み合わせ | ダッシュからジャンプへつなぐ区間を含む総合コース |

通常ルートを慣れたプレイヤーが走った場合、1コース30秒〜2分程度を目安にする。初見や全タルト収集でこれを超えることは許容する。

実装指針：タルトを道案内として配置し、ジャンプ先や推奨進路が読み取れるようにする。少なくとも各コースに途中チェックポイントを設け、長い区間や難所に応じて追加する。難所を増やす場合も、初回から動く足場・敵・新しいギミックを追加する必要はない。

### 7.2 ダッシュパネル

- 球がパネルに乗ると自動発動し、設定された方向へ加速する。
- 発動方向を矢印等で視覚的に示す。
- 接触中に毎フレーム加速が累積して無限に速くならないようにする。
- 同一ラウンドでも、離れて再び踏めば再利用できる。

### 7.3 ジャンプ台

- 球が台を踏むと自動で跳ぶ。
- 水平方向の速度を活かし、ダッシュ後に踏むとダッシュジャンプが成立する。
- 横や下面から接触しただけで不自然に発動しないようにする。
- 1回の接触で連続発動しないようにする。
- 着地先は通常カメラで見える位置に配置する。

### 7.4 ゴール

- 球がゴール領域へ入ると、そのラウンドをクリアとする。
- タイムとタルト数を確定し、以降の接触や落下によって結果を変えない。
- ゴール処理・記録保存・リザルト遷移は1回だけ実行する。

実装指針：ゴールや収集物にはセンサー／重なり判定を利用し、物理的に球を停止させることをクリア成立の条件にしない。

## 8. 落下とチェックポイント復帰

この節は、発注者による最後の修正を反映した確定仕様である。

### 8.1 復帰先の優先順位

1. **通常の落下**：落ちた場所そのものではなく、少し前に安定して通過した安全な道へ戻す。
2. **安全な復帰先がない、または復帰が危険・詰みにつながる場合**：最後に通過したチェックポイントへ戻す。
3. **まだチェックポイントを通過していない場合のみ**：安全な履歴がなければスタートへ戻す。

チェックポイント通過後に、安全な履歴がないことを理由としてスタートへ戻してはならない。

### 8.2 復帰時の共通処理

- 球の移動速度・回転速度をリセットする。
- タイムを止めず、同じラウンドを継続する。
- 取得済みタルトと通過済みチェックポイントを保持する。
- 短い落下／復帰演出の後に再操作できるようにする。
- コース全体を再読み込みする必要はない。

### 8.3 安全な履歴の扱い

以下は確定した体験を満たすための実装指針。

- 一定時間以上安定して接地した地点を、有限の履歴として記録する。
- 足場の端、空中、ダッシュパネル上、ジャンプ台上、頭上が塞がった地点等を候補から除く。
- 落下直前の最新座標をそのまま採用せず、時間または距離をさかのぼる。
- チェックポイント更新時には、以前の区間へ不必要に戻らないよう履歴を整理する。
- 復帰後は古い危険な履歴が繰り返し選ばれないようにする。
- 手続き的な安全判定が不安定な箇所は、コースデータに復帰可能領域・復帰禁止領域を定義してよい。

### 8.4 危険・詰みの判定

「危険と判断する」はAIによる曖昧な判定を意味しない。次のような再現可能な条件で処理する。

- 候補地点に球が安定して載る支持面や必要な空間がない。
- 復帰地点から短時間で再落下する状態を繰り返している。
- 自動発動ギミック上へ復帰し、操作の余地なく再落下する。
- 通常の操作でコースへ復帰できない場所に候補がある。

実装指針：同じ復帰候補で短時間の再落下が2回続いたら、チェックポイントへ切り替える等の上限を設ける。回数・時間・履歴をさかのぼる量は調整項目とし、設定値にまとめる。

チェックポイント自体は、停止状態の球を置ける十分な広さと、通常ルートに戻れる経路を持つ安全な地点にする。復帰した瞬間に以前の強い傾き入力が作用して落ちないよう、短い入力抑制や再開導線を調整する。

## 9. タイム・タルト・記録

### 9.1 タイム

- 操作準備と素材読み込みは計測に含めない。操作可能なコース開始時点から計測する。
- ゴール成立時点で止める。
- 落下演出、復帰処理、一時中断、バックグラウンド滞在は経過時間に含める。
- 中断やバックグラウンド中は物理シミュレーションを止め、戻ったときに再開操作を挟む。
- 再開時に長時間分の物理更新を一度に実行しない。
- 単純な描画フレーム数の加算で計測しない。

実装指針：表示は分・秒・百分の一秒等で統一する。厳密な不正対策や端末時刻改変対策は今回の対象外。

### 9.2 タルト

- 各コースのタルトには一意のIDを付ける。
- 取得後は見た目と取得判定を無効化し、演出と1ポイントの加算を1回だけ行う。
- 落下しても取得状態を保持し、取り直して点数を増やせないようにする。
- 再挑戦で全タルトを初期状態へ戻す。
- 全収集は達成表示を追加するが、ゴールの必須条件にしない。

### 9.3 保存

- ベストタイムは小さい値を採用する。
- 最多タルト数は大きい値を採用する。
- 両記録は独立して更新する。別ラウンド由来の記録である可能性を前提とし、1回の成績のように合算しない。
- 記録更新はコースクリア時に行う。途中離脱したラウンドは更新対象にしない。
- 保存先は同じブラウザ・同じ公開先のローカル領域とする。端末間同期はしない。

実装指針：localStorage等を使用し、形式にバージョンを持たせる。保存不可・破損データでもゲームを起動可能にし、保存できない場合は短く案内する。ブラウザのデータ削除で記録が消えることをREADMEまたは案内に記載する。

## 10. 見た目・音・モバイル品質

### 10.1 アート方針

- 青空と白い雲を背景に、浮島・空中の道でコースを構成する。
- ポップで明るく、キャラクターを見せる配色にする。
- 床、縁、ダッシュ、ジャンプ、タルト、ゴールは見分けられるようにする。
- 落下地点やジャンプ先を雲や装飾で隠さない。
- 透明球は、中身が見えることと外形が分かることを両立する。
- タルトはタルトと認識できる簡単な3D表現でよい。専用モデル支給は前提にしない。
- 5コースは共通の世界観・素材を再利用してよい。5種類の独立した美術セットは不要。

### 10.2 音と演出

タルト取得、ダッシュ、ジャンプ、落下、チェックポイント、ゴールの出来事が分かる短いフィードバックを用意する。すべてに派手な演出を付ける必要はない。音を消しても必要情報が伝わるようにする。

効果音とミュートは必須。BGM、新規キャラクターボイス、長いムービーは対象外。音の開始はブラウザのユーザー操作条件に合わせる。

### 10.3 表示と負荷

- ノッチ、ホームインジケーター、ブラウザのアドレスバーを考慮し、操作UIが隠れないようにする。
- ゲーム操作中の意図しないページスクロールや拡大で操作が途切れないようにする。
- 横向き時は縦持ち案内を表示する方針とし、ブラウザの画面回転ロック成功を動作条件にしない。
- iPadでは余白・UIサイズ・カメラ構図を調整する。横画面専用UIの制作は対象外。

性能の推奨目標は通常プレイ60fps、合意した検証端末で継続的に30fpsを下回らないこと。**これは会話で確定した端末別保証値ではないため、検証端末の選定時に受入目標として合意する。** 解像度上限、影、透明表現、装飾密度を調整し、入力応答を優先する。

## 17. 最終的な判断基準

本作は「多機能な球転がし基盤」ではなく、スマホの傾き、慣性、落下の緊張感、ダッシュジャンプ、短い再挑戦を楽しめる5コースのゲームとして仕上げる。

迷った場合は、①スマホで正しく操れる、②安全に再挑戦できる、③次に進む道が分かる、④ゴールが気持ちよい、の順に優先する。必要な機能を仕上げ、追加機能で複雑にしない。
